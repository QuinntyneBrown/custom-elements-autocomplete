# Detailed requirements

## L2-001: Library and applications

**Traces to:** L1-001

1. Given a clean install, when type checking and library/demo builds run, then they succeed and the library emits ES modules and declarations.
2. Given the dev or e2e app, when it loads, then it imports the same production component library.
3. Given a provider configured before connection, when search runs, then it receives the trimmed query and an abort signal; an unconfigured component makes no requests and shows configuration guidance.

## L2-002: Debounced search and query changes

**Traces to:** L1-002

1. Given typing or paste, when 200 ms elapse after the latest input, then exactly one provider call uses the latest nonblank query.
2. Given pending or displayed results, when input becomes blank, then results clear immediately and pending work is canceled.
3. Given a previous request, when the query changes, then that request is aborted and its late response cannot change the current state.
4. Given a scheduled or running search, when the provider changes, then previous work is canceled and no new search begins until input changes.

## L2-003: Results and selection

**Traces to:** L1-002

1. Given matching products, when results render, then names and thumbnails are visible.
2. Given a product, when its expand button is activated, then category, volume, formatted price, and tasting notes are visible.
3. Given an expanded product, when selected again, then it remains expanded; selecting another product collapses the previous one.
4. Given missing or broken product images, when displayed, then a built-in fallback and meaningful image alternatives are available.
5. Given new data for an existing result ID, when assigned, then the visible result and details update.

## L2-004: Search states and recovery

**Traces to:** L1-002

1. Given a pending search, when displayed, then a loading status is visible.
2. Given no matches, when search completes, then an empty-results status is visible.
3. Given a rejected search, when it fails, then a useful error is visible and a later search can succeed.

## L2-005: Lifecycle and independence

**Traces to:** L1-001

1. Given a disconnected element, when input or a pending request completes, then no search or detached-state update occurs.
2. Given a reconnected element, when typing resumes, then a single subscription searches normally without recreating the Shadow DOM.
3. Given multiple instances, when one is used, then the others retain their own query, results, and selection.
4. Given supporting elements removed and reinserted, when rendered, then their content and interaction remain usable.

## L2-006: Accessible and responsive examples

**Traces to:** L1-003

1. Given any example, when inspected, then inputs have accessible names, status changes are announced, buttons work by keyboard, and focus indicators are visible.
2. Given widths of 375, 576, 768, 992, and 1280 pixels, when results and details appear, then there is no horizontal document overflow or clipped details.
3. Given fixture content containing HTML markup, when rendered, then it appears as text without script execution.
4. Given local examples, when they run, then no API credentials, remote product images, or external fonts are required.

## L2-007: Automated suites

**Traces to:** L1-004

1. Given Jest, when unit tests run, then debounce boundaries, cancellation, recovery, lifecycle, selection, and formatting are tested using controlled time and providers.
2. Given Playwright, when desktop and mobile projects run, then acceptance tests use page objects against the e2e app and retain failure artifacts.
3. Given CI, when validation runs, then type checking, both builds, Jest, and Playwright must pass.
